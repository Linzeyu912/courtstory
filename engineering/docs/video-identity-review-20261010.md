# 第一部分：视频身份初稿与人工审核

日期：2026-10-10，Asia/Shanghai。状态：本地初稿流程已接通，真实任务的人工编辑、保存和第三部分读取已验证。本轮未提交、未推送、未部署。

本轮把第一部分球员标定接到第三部分已经使用的视频阅读工具上：一次启动后，先取得真实人物观察，再由 Agent 阅读总览、按需回看时间窗口和人物区域，建立暂定的 P 身份及有名单依据的姓名，最后由人核对、修正。原有逐帧编辑、范围关联、保存和撤销继续使用。

用户确认 Agent **只负责初步处理，不要求十分精确**。本轮验收目标是“生成可以审核的初稿 → 人工改、补、保存 → 第三部分继续使用”。匿名 P、`UNKNOWN` 和 `partial` 都可以是正常输出；成功不按姓名数量判定，也不要求全员姓名、全片完整覆盖或准确率提升评测。来源不符、没有有效响应、损坏人工修改或无法保存衔接仍属于实际问题，不能用“允许不精确”掩盖。

本轮资料与真实验收范围是 **2024-25、2025-26 两个赛季的火箭相关视频**，不包括 2026-27。赛季名单、比赛名单和球衣号码必须与素材实际来源相符；不根据视频文件名或球衣外观猜比赛日期、对手或赛季。两个赛季的数据入口见 [2K 数据说明](../../2K%20Player%20Data/README.md) 与 [比赛名单](../../data/player-rosters/README.md)。

## 怎么使用

1. 在现有视频库选择或导入素材，进入“球员标定”。页面载入后自动启动一次身份初检；无需先逐人保存参考，也无需再点击单独的“识别姓名”才开始新流程。
2. 若已经知道赛季、红组 A／蓝组 B 对应的实际球队或明确的 NBA 比赛编号，在现有姓名表单填写。已保存的上下文会自动读取；不完整的信息可以留空，缺少可靠名单依据时保留匿名 P。更改这些字段后，旧任务会过期，应使用更新／重试入口按新上下文检查。
3. 等待人物观察准备和 Agent 阅读。原来采用“直接人工制作”的素材没有检测框时，会调用视频库现有检测流程，载入检测结果后继续初检。检测器缺权重、检测失败或没有可用人物观察时，会显示实际原因，不能把该状态当作初稿完成。
4. 查看初检提示中的错人、裁判、身份断开、缺测和冲突，点击提示定位画面。按制作需要播放或逐帧检查 P 对应的人，优先处理遮挡前后、临时 T 变化、切镜和换人附近；不要求先把全片全部核验完才能继续。
5. 用现有点人、选择 P、范围关联、排除非球员、交换槽位、姓名确认和位置编辑修正。人工确认只记录实际审核的内容；把机器候选加入草稿，不会自动把整段标成“人工已确认”。
6. 修改自动保存到当前浏览器草稿，使用“撤销”可回到上一状态。新初检的身份与姓名在一次更新中加入，撤销该次更新会一起撤回。之后进入第三部分战术制作，读取当前保存的身份与姓名快照。

红／蓝只是工作台的两组槽位，不等于球衣实色或攻守角色。P 是需要审核的人物身份槽位，T 是检测跟踪产生的临时编号；编号连续或姓名标签稳定，都不能证明全片始终是同一真人。号码 `0` 与 `00` 分开保存。原有单独姓名识别、号码读取和固定身份续接入口继续用于补查，详见 [姓名识别](player-name-identification-20261007.md)、[v4 姓名规则](player-name-optimization-20261007.md)和[人工修正](manual-player-correction-20261007.md)。

## 检测准备与草稿保护

已有有效人物框时直接使用该版本观察。没有有效观察时，前端通过视频库的 `process` 接口准备默认 `team-stable` 结果，并读取真实返回的检测版本。它不把“空输入”包装成已完成身份结果，也不按模型描述生成坐标。

自动迁移原人工稿必须同时满足视频哈希、尺寸、帧数、逐帧编号和时间完全一致，且原稿没有旧的正 T 编号关联。原稿先保存；目标检测版本已有独立草稿时，也不会覆盖它。时间基准不一致、存在旧 T 关联或目标稿已存在时，界面会明确要求从视频库打开目标版本核对，两个草稿都保留。此处保留兼容的人工坐标，不代表重新验证了坐标或真人身份。

检测框仍可能漏人、包含观众或裁判，也可能串人。没有真实观察的位置保持空白；已有人工补点继续按原来源保存。屏幕位置、框底中心或平滑轨迹不等于已经验证的脚部接地点或米制位置。

## Agent 阅读与姓名机制

后端复用第三部分的 `CommentaryVideo` 解码、总览、源帧窗口、区域图片工具和 provider。第一部分使用独立身份任务提示及保存工具，不会把第三部分解说文本直接当作人物身份依据。实现入口是 [identity_video.py](../scripts/identity_video.py)、[identity-tools.mjs](../tools/player-review/agents/identity-tools.mjs)和[identity-worker.mjs](../tools/player-review/agents/identity-worker.mjs)。

每条可采用关联都必须落到当前素材实际存在的有限 T 观察区间。宿主检查来源哈希、实际读取图片、帧时间／PTS、区间端点、缺测、切镜、风险和冲突；未读过的画面不能仅凭模型声称“看过”就成为证据。号码需要能定位到目标人物的原帧或有效局部图。区间不能任意跨过缺测、切镜、检测跳变或过大的证据间隔。

Agent 提交人物、角色、区间和可见号码证据，宿主使用明确赛季／球队／比赛上下文查询名单。只有唯一匹配才产生姓名候选；不匹配、同号不唯一、人物关联冲突或没有清晰号码时保持未知。姓名 profile 是证据摘要，不能把姓名延伸到没有证明的 T 或整片。不会使用人脸识别或虚构能力分数补齐未知信息。

前端先验证并应用身份，再把姓名限制到实际通过保护检查的 P／T／帧交集。姓名包与身份包作为一个草稿更新提交；嵌套姓名包来源不符时整次更新失败，不留下只改了一半的身份。机器结果保留 `identityVerified:false` 与待审核状态，明确人工姓名、来源匹配的已确认 profile、人工区间、排除、位置和审核记录优先。

## 部分结果、缓存与重试

`ready` 表示任务已有可读候选，不一定表示全片检查完成；还须读取 `candidate.completionStatus`。`partial` 会显示“部分证据已整理，仍有区间待检查”，并提供“继续检查未完成区间”。可用部分可以先加入草稿，其他部分继续留待核对；用户也可直接人工补充，不必为了把状态改成完整而反复调用模型。

显式继续会发送当前草稿及 `forceRetry:true`。同源任务从已有检查点续接，重新验证旧图像来源，合并已保存证据；当前实现最多允许两轮局部续接。不会因刷新页面或一个暂时错误无限重跑整片。已完成候选因草稿变化不能直接采用时，可以复用缓存，再按当前人工记录重新检查。

原始槽位基线在续接中保留。前端只有在算法、来源、上一任务关系、原始输入槽位和上次实际应用后的槽位都精确匹配时，才把差异认作自己的上一轮机器更新。人工在两轮之间改过姓名、profile、绑定或其他受保护槽位记录时，该槽位仍被保护，不能借“续接”覆盖人工修改。取消、换素材、换检测版本或迟到响应也不会自动覆盖新稿。

缓存键包含视频／跟踪来源、算法、明确身份上下文和宿主模型配置。更改赛季、球队、比赛或模型配置不能复用旧名单结论。一次采用后的姓名和旧机器纠正记录也不能跟随新的 P／T 关联串入另一人物。

## 与第三部分的衔接

现有草稿保存、`exportReview` 和姓名读取函数仍是数据来源。第三部分的 review snapshot 与 name overlay snapshot 会取得当前已保存的有限姓名、位置和候选来源，不需要再执行另一套姓名识别。前端测试已覆盖“新初检 → 自动保存 → 第三部分快照 → 人工修改 → 撤销”，但这只证明数据衔接，不证明模型把真人认对。

机器姓名进入第三部分后仍是候选。出现姓名、位置或身份争议时，应回到第一部分核对，不能把待审核状态在后续解说或成片中静默升级成已确认事实。已有第三部分计划和成片的版本／失效规则继续按[解说与配音工作流](commentary-narration-workflow.md)执行。
