# 报名准备指南

## 报名材料要让读者看清什么
报名阶段的目标是让组委会能够判断：我们理解赛题，有与任务相关的真实能力和交付经历，并且能完成组队与线下参赛。官网未公开报名筛选权重，下面是根据报名问题和作品要求提出的写作建议，不代表组委会内部标准，也不保证入围。

作品需要把视频和深度数据转化为画面标注与同步解说。因此，材料中最有价值的内容不是技术名词数量，而是“做过什么、本人负责什么、怎样做、结果怎样、与本次任务有什么关联”。没有篮球或 AWS 经历也应如实说明，用可迁移的经历支撑能力。

先区分两个目标：9 月 24 日公布的是入围参赛资格；澳门 TOP 8 决赛资格要在 10 月 10 日通过现场作品评审获得。报名材料和后续作品都重要，但二者不是同一轮评选。

## 个人简介如何准备
个人简介上限为 1000 字。建议先准备一份约 400 至 700 字的事实草稿，留出修改余地；这是内部写作建议，不是官方建议字数。组织顺序可以是：当前身份与主要方向、最相关的能力和项目、拟承担的角色、对比赛任务的理解。

- 开头说明真实背景与最相关能力，例如数据处理、视觉分析、视频工程、前端可视化、产品设计或篮球内容分析，优先保留与赛题有关的内容。
- 选择一至两个最有证据的项目，说明本人具体完成的模块。团队成果与个人贡献分别表述。
- 用已核验的信息体现成果，例如已上线功能、公开演示、测试样本数量、明确条件下的性能结果或真实用户反馈。没有测量就不要写精确提升比例。
- 说明这些经历能够支持本次哪一环：视频与数据接入、回合分析、视觉叠加、同步解说、产品整合或现场演示。
- 拟承担的角色用计划语气表达，不把尚未实现的能力或合作写成既成事实。

供整理事实的结构：我目前从事或学习什么；最相关的项目是什么；我负责哪部分；有什么结果和证据；这些经验如何用于本次比赛。此结构不是可直接提交的个人简介，需由本人补充事实后再组织语言。

避免“熟练掌握所有主流模型”“热爱 AI 并富有创新精神”一类没有证据的陈述。没有必要写满 1000 字，也不要把简介写成项目名和工具名堆积。

## 开发经历如何选择和描述
题目要求描述印象最深的一次黑客松或开发经验，包括做了什么、结果如何，上限 1000 字。它明确允许开发经验，不需要为了贴近赛事而虚构黑客松经历。

优先选择能够同时说明本人贡献、技术或产品难点以及实际结果的一次经历。与视频、数据、可视化或 Agent 相关的项目更容易建立关联，但关联性应服从事实。

可按以下顺序整理：
1. 背景与目标：谁遇到什么问题，项目希望完成什么。
2. 本人职责：负责哪些具体模块，与队友如何衔接。
3. 关键难点：例如数据质量、同步误差、模型输出不稳定、部署或交互问题；写真实遇到的一项即可。
4. 采取的办法：说明关键决策及原因，而非只列出技术栈。
5. 结果与验证：交付物是什么，如何验证，仍有哪些局限。
6. 与本次比赛的联系：哪些经验可以迁移到篮球视频与数据解读。

有失败或未完成部分时，可以写清问题、定位过程和学习结果。可核查的有限成果，比没有依据的“大幅提升”“行业领先”更有说服力。

## AWS 使用经验和其他事实字段
AWS 是多选题，当前可见选项包括从未使用过、EC2、S3、Bedrock、QuickSight、其他。按实际使用情况选择；阅读过文档、看过演示，不等于有实操经验。

内部先整理每项服务的使用场景、本人操作、完成的结果和可证明材料。如只是教程练习，可以明确写为练习；如无 AWS 经历，选择真实选项，在简介中说明已有的相关工程经验，不能把将来的学习计划写成已完成经历。

姓名、手机、邮箱、公司或学校、地区及竞赛次数应准确一致。身份证明、参赛次数的完整下拉选项仍需实际填写时核对。联系邮箱应由本人正常使用，避免漏收资格通知。

港澳通行证问题与全程参与问题需要按真实状态回答。港澳通行证有效与具备实际通关条件不应混为一谈；具体签注和通关安排以赛事通知及有关官方要求为准。此处不作资格或出入境判定。

生活照按表单格式和大小要求准备即可。照片清晰、内容真实；不把个人外貌作为竞争力论据。此类材料不需要放入团队公开作品仓库。

## 篮球理解问题如何准备
题目要求至少列举 3 个影响投篮命中概率的因素，上限 100 字。适合列出清晰、不同维度的因素，并保持表述准确，不需要写成长篇战术分析。

用于理解的候选维度包括出手位置与距离、防守干扰、投篮姿态和平衡、移动与转身状态。NBA 官方 xFG% 说明涉及这些方向，可作为阅读材料；这不是要求照抄的报名答案。队员应选择自己能够解释的因素，用自己的语言完成最终回答。

这里要分清两个问题：“哪些因素一般会影响命中”与“官方 xFG% 模型使用了哪些特征”。官方说明中的 xFG% 不纳入球员身份、进攻时钟和分差；不能把这些说成该模型现有输入。来源见后文 NBA 指标说明。

## 团队内部先整理的证据
下表用于讨论和检查，不是官网新增的提交材料要求。表单若没有附件或链接字段，不应假定必须额外提交。

| 材料 | 建议记录的内容 | 用于支持什么 |
|---|---|---|
| 成员能力记录 | 每人的主要能力、拟承担角色、可投入时间 | 分工是否覆盖赛题关键环节 |
| 项目事实卡 | 项目目标、本人职责、关键办法、结果、局限 | 个人简介与开发经历 |
| 可展示证据 | 合法可分享的仓库、演示、截图或项目说明 | 让经历可核查 |
| 指标记录 | 测试条件、样本范围、结果、测量时间 | 避免无依据的量化表达 |
| 篮球知识笔记 | 每个指标的含义、适用范围和容易混淆处 | 对赛题及篮球问题的理解 |
| 参赛安排 | 组队状态、到场时间、证件实际情况 | 判断能否完成线下活动 |

证据选择的内部优先顺序是：真实可展示的成果、清晰的本人贡献、与赛题的关联、可验证结果。没有公开链接的经历仍可描述，但不要泄露公司、客户或其他人的非公开资料。

## 讨论后再定稿的检查顺序
1. 每名队员先列事实，不急于润色；队内确认个人贡献和结果表述。
2. 共同明确我们最能做好的部分，以及尚缺的能力。至少覆盖数据与分析、画面与产品呈现、整合交付，但不必一人只承担一个角色。
3. 选出每人最相关的一次开发经历，避免多人写成完全相同的履历。
4. 再压缩到表单上限，检查姓名、项目名、数字、职责及选项是否一致。
5. 对照真实报名页检查最新问题、组队流程、条款与截止时间；讨论确认后再填写提交。

以上步骤是内部准备建议。本轮文件只帮助理解与准备，不包含替任何成员填写的个人资料，也不进行报名提交。
