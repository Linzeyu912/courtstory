# 原视频战术标注的位置提取与 RelateAnything 评估

- 核验日期：2026-10-01（Asia/Shanghai）。
- 状态：源码与文档调研完成；以下实现路线和接口为建议，尚未运行篮球样片或确定模型选型。
- 依据：本轮用户口述、[已有方案总结](../docs/agent-concept-review.md)及文末一手来源。
- 核验版本：RelateAnything `06766fdf56752ca535fc9b971fca99ce563676d0`。动态官方文档以本次读取为准。

## 结论

建议先用人物检测与跟踪、脚下锚点估计、球场平面映射，完成原视频上的稳定标注。RelateAnything 可接在检测结果之后，为区域之间的关系提供候选判断；是否采用，取决于它在篮球样片上能否优于几何与时序规则。

用户确认的产品方向是保留原视频，叠加虚线箭头、人物高亮、空位标记及同步解说。后台可以维护球场坐标，供透视变换和距离计算使用；观众看到的仍是原比赛画面。三个模块继续沿用“数据采集 → 数据处理 → 内容呈现”，无需因此新增产品模块。

## 三个模块的接口

| 模块 | 本次关注的工作 | 交给下游的内容 |
|---|---|---|
| 数据采集 | 读取原视频、时间信息、官方配套数据；按需补充球员资料和标注样本 | 视频与来源、视频时间基准、可用数据字段及缺失情况 |
| 数据处理 | 切镜头识别、球员和球检测、跨帧关联、脚下定位、球场标定、轨迹与关系判断 | 带时间、坐标系、稳定对象编号和质量标记的数据 |
| 内容呈现 | 按讲解时间生成路径、圆环、文字和局部高亮；处理透视、遮挡与淡入淡出 | 叠加图层、解说时间轴和成片 |

公开资料适合补充球员身份与背景，逐帧位置必须来自对应视频或与其对齐的配套数据。网络素材可以作为验证或训练样本；是否需要训练，先由现有模型的错误决定。

## RelateAnything 的实际能力

| 问题 | 核验结果 | 对本项目的含义 |
|---|---|---|
| 输入是什么 | 单张图像、外部提供的目标框，可选蒙版及关系词表 | 可以接收 YOLO 等工具的结果 |
| 输出是什么 | 主体区域、关系词、客体区域和分数 | 可构成画面中的关系图 |
| 能否自己找人 | 核心关系模型不检测目标；演示组合了独立检测器 | 人物、篮球的定位仍需独立完成 |
| 能否跟踪视频 | 核心 API 逐图推理；视频示例另有目标关联和关系稳定处理 | 应区分核心模型与示例管线的能力 |
| 能否求球场透视 | 本次核验的 API 没有输出球场对应点、单应矩阵或相机姿态 | 地面贴图仍需球场标定 |
| 能否判断篮球战术 | 允许自定义关系词，但本次未找到该固定版本提供篮球战术专项验证 | 添加“掩护”“换防”等词，不等于已可靠识别这些事件 |

输入输出依据：[README][ra-readme]、[Quickstart][ra-quickstart]和 [API 源码][ra-api]。视频示例的 `Tracker` 使用 Kalman 框状态和两阶段 IoU 关联，另有关系分数平滑与迟滞逻辑；这些是可研究的工程实现，本次未验证其篮球跟踪效果。[视频源码][ra-video]

关系图表达的是“对象 A 与对象 B 有什么关系”。人物框和蒙版来自上游；返回的框不是该模型重新测得的地面坐标。`box_labels` 只影响显示，把标签写成球员姓名或战术角色不会向模型注入这些知识。[Quickstart][ra-quickstart]

### 适合测试的用途

- 将人物、篮球等已定位区域送入模型，检查接触或持球相关候选关系是否有用。
- 以少量明确词汇做对照实验，比较加入关系模型前后的误报和漏报。
- 将模型结果作为时序分析的证据之一，保存原始分数与来源。

“左侧”“接近”等几何关系可直接从坐标计算。掩护、换防、协防、传球需要观察一段时间内的队伍、人物轨迹、球权及相互作用；单帧关系分数不足以确认。最近的防守人也不必然是正在负责防守该人的球员。这些是本项目的设计判断。

### 接入前要核对的源码细节

1. **区域编号需要自行映射到跟踪编号。** `subject_idx` 和 `object_idx` 属于当前输入区域序列。源码在超过 `max_boxes` 时会截取或重排区域，再返回处理后序列的编号。建议调用前自行筛选，并保留 `region_index → track_id` 映射。
2. **分数的文档描述与当前实现有差异。** Quickstart 称检测置信度只改变排序；该版本 `predict` 的普通返回路径实际把检测置信度乘入返回的 `Triplet.score`。双图路径还没有走普通路径的 `self.contract.scores`。接入前应做小规模一致性检查，明确保存的是关系分数还是融合后的排序分数。
3. **换词表后重新核验阈值。** 自定义篮球词没有现成的专项校准；分数不能直接解释成“该战术有多少概率成立”。阈值应在篮球标注集上调试，并在独立比赛素材上评价。

以上第 1、2 点来自固定版本 [API 源码][ra-api]的静态检查；第 3 点参考 [Quickstart][ra-quickstart]和 [Pitfalls][ra-pitfalls]。尚未运行模型复现，不声称已经测得错误率。

### 规模和运行成本

作者推荐的 `relsgg-vits16plus` 为 53.2M 参数。README 报告在 RTX 3080 Laptop GPU 上，TensorRT FP32 关系推理为 17.2 ms，加入 YOLO26m 检测后为 36.5 ms；条件为 batch 1、35 种关系、6 张样图、预热后的中位耗时，排除加载和初始化。这是作者报告，不能外推为本机完整篮球处理管线的帧率。[README][ra-readme]

`pyproject.toml` 要求 Python 3.12 及以上，并约束 PyTorch 等依赖版本。CPU、GPU和导出运行路径需按实际设备验证。本轮只读取源码，没有安装依赖、下载模型或测试显存与耗时。[依赖声明][ra-pyproject]

## 让图形贴到球场和球员脚下

### 人物位置和人物身份分开保存

YOLOv8 有检测、姿态与分割等不同任务变体，通常需要选择对应权重；普通检测权重不会同时自动给出脚踝与人物蒙版。YOLO 属于深度学习视觉模型。[YOLOv8 官方说明][yolov8]

建议先比较以下组合：

- 人物检测配合 ByteTrack，作为基础跟踪方案。
- 人物检测配合 BoT-SORT，测试镜头移动补偿和可选外观关联是否改善编号串换。
- 姿态模型提供脚踝等关键点；分割模型提供前景蒙版。只为需要的效果加入相应能力。

跟踪输出对象编号，姿态输出关键点坐标与置信度，分别见[跟踪文档][tracking]和[姿态文档][pose]。这里的 `track_id` 表示镜头内连续出现的对象；球员姓名需要另外结合队伍、号码、名单和复核，无法确认时保持未知。检测出的观众、裁判或场边人员也需过滤，不能把全部 `person` 都当作场上球员。

### 脚下锚点

第一版可把人物框底边中心作为粗略锚点；进一步结合可见脚踝、鞋底附近蒙版与接地状态，估计人物在地面上的位置。脚踝不等于鞋底接触点，双脚中点也只是一种近似。

起跳、倒地、遮挡和截断都会破坏这个近似。建议给每个锚点保存方法、可见性和质量状态；仅在短时间内允许基于已确认地面轨迹估计，可靠性不足时隐藏标注。模型预测点和人工确认点应能区分。

### 从场地线得到透视映射

用户提出的场地线、交点和端点是合理线索。建议将画面上的底线、边线、罚球线或禁区角点，与正确球场模板中的对应位置关联，求 **单应矩阵 Homography**，即地面与图像之间的平面映射。

点对应方法至少需要 4 组处于一般位置的正确对应点；不能把集中在一条线上的点当作充分约束。实际宜使用更多且分布良好的点或线约束，并检查重投影误差。图像边缘造成的线段截断不能直接当作球场真实端点。[OpenCV 对应点说明][opencv-points]

统一把 `H_court_to_image(t)` 定义为时刻 `t` 从球场地面坐标到原图像素的变换：

```text
图像齐次点 ∝ H_court_to_image(t) × [court_x, court_y, 1]
```

矩阵相乘后除以第三个分量，得到像素坐标。有效且可逆时可用逆矩阵估计接地点的球场坐标。后台的平面坐标用于计算，最终图形仍投影回原视频。

对贴地箭头、地面圆环而言，这种映射通常已够用。若确实需要相机的物理俯仰角、位置等信息，还需相机内参或额外可靠约束；只凭一个任意形状不能唯一确定相机角度。[OpenCV 单应与相机姿态说明][opencv-h]

### 镜头变化与遮挡

- **推拉摇移时更新映射。** 固定一个 `H` 用完整段视频会使地面图形漂移。可从人工标定关键帧起步，用场地静态特征传播，并定期重新标定。
- **切镜头时重建状态。** 新镜头重新标定；跨镜头身份关联应另行确认，不能默认继承旧编号。
- **历史轨迹用当前映射绘制。** 将过去的位置存成球场坐标，再用当前帧 `H(t)` 投影全部轨迹；直接连过去各帧的像素点会混入摄像机运动。
- **人物遮住地面图形。** 先合成地面图层，再用对应帧的前景人物蒙版恢复人体区域，使箭头经过腿部时被合理遮住。姓名标签等界面元素另按显示需求处理。
- **区分地面与空中对象。** 球在空中的像素位置不能直接通过地面单应矩阵变成真实落地点。第一版传球箭头可表示已确认的传球方向，不声称重建了球的三维飞行轨迹。

这些为基于平面成像原理的实现建议，尚未进行视觉验证。相机补偿、平滑与蒙版也可能产生延迟或边缘误差，应以成片检查为准。

## 建议保存的数据

以下是内部接口草案，不代表主办方已提供的字段。

| 数据组 | 最小内容 | 约定 |
|---|---|---|
| 帧与时间 | `video_id`, `shot_id`, `frame_index`, `pts_ms`, 图像宽高 | 优先使用解码时间戳；比赛时钟另存并记录对齐关系 |
| 人物对象 | `track_id`, `bbox_xyxy`, `team_id`, `player_id` | 检测框为原图像素；队伍与身份可为空；保存检测置信度 |
| 接地锚点 | `anchor_image_xy`, `anchor_court_xy`, `method`, `visibility`, `quality` | 球场坐标可为空；单独标明测量、估计或人工确认 |
| 球场映射 | `H_court_to_image`, 模板标识、坐标原点/轴向/单位、有效范围、误差 | 校准点不足或失效时明确标记，不输出伪精确距离 |
| 前景蒙版 | `mask_ref`, 对象编号、时间戳、分辨率、缩放变换 | 蒙版与视频帧严格对应；可按需生成 |
| 球与球权 | 球的图像位置、可见性、候选持球对象、证据 | 离地球不强行填写地面坐标；球权允许未知 |
| 关系与事件 | 主客体编号、关系、起止时间、证据来源、分数类型、确认状态 | 区分规则判断、模型候选、人工确认和讲解推断 |
| 呈现指令 | 图形类型、跟随对象、路径/区域、坐标系、起止时间、关联事件 | 区分已观察轨迹与复盘示意；和语音共用时间轴 |

图像缩放、裁剪、补边以及最终播放器缩放都需保留变换关系。建议以解码后的原视频像素为基础，将模型坐标先还原，再由呈现层统一适配尺寸。

## 最小验证顺序

1. **验证原视频叠加。** 选连续镜头，人工标定少量球场点，检测和跟踪关键球员，生成脚下圆环与一条贴地路线。先验证位置和透视是否稳定。
2. **验证遮挡与镜头变化。** 加入人物蒙版，测试重叠、起跳、摇移与切镜头时的降级处理。
3. **验证战术所需的证据。** 加入篮球定位、队伍关联和时间窗，先做接近、分离、移动方向及球转移等可核对事件。
4. **对照测试 RelateAnything。** 固定相同视频、检测框、跟踪编号和评价片段，比较“几何＋时序规则”与“加入关系候选”两条路线；只在增益明确时保留模型。

可先从[现有100段素材索引](../data/videos/nba/2024-25/INDEX.md)选择 001（挡拆外弹）、002（突破分球）、003（短顺下）、014（包夹后顺下）、017（追防切球）、025（长传转换）作为候选。这里只依据已有标签选题，本轮没有重新看片确认可标定性。当前素材库有片段标签，不能视为已有逐帧检测框、脚下点或关系真值。

评价建议：

- 记录接地点误差、场地独立核验点的重投影误差，报告中位数和较大误差；同时报告分辨率、遮挡和失效帧比例。
- 统计编号串换、跟踪中断，以及箭头是否贴地、是否穿过人体、转镜后是否正确消失。
- 关系判断加入负例，如“靠近但没有掩护”“距离最近但没有负责防守”；报告精确率和召回率，不只看片段成功截图。
- 按比赛或原视频划分调试集与评价集；相邻帧、同一回合或重叠裁剪不能分到两侧。
- 在目标设备测量解码、检测、跟踪、姿态/分割、关系推理、合成与编码的总耗时，并记录峰值显存。正式验收阈值待样片结果后商定。

这些是后续实验安排，未作为已完成结果登记。无需先采集更多视频或训练自有模型；优先用已入库素材明确失败类型，再补标注或定向采集。
